## 1. Зачем нужен treasury-модуль

Бизнес-модель платформы предполагает, что merchants берут batch-партии чеков **на реализацию** и рассчитываются с Issuer только после продажи чеков, обычно ежемесячно. Это означает, что между моментом отгрузки batch-партии merchant и моментом получения оплаты возникает funding gap до 30 дней.

Чтобы платформа продолжала работать без перебоев в этот период, требуется внешнее финансирование. Treasury-модуль как раз решает эту задачу: он привлекает credit lines от инвесторов и lenders и распределяет их на merchant funding в соответствии с заданным для платформы risk appetite.

**Упрощенная модель:**

`Lenders → Credit lines → Platform → Merchant funding → Settlement → Repayment to lenders`

Платформа зарабатывает на спреде:

**merchant fee income − interest expense on credit lines = net carry**

## 2. Lenders платформы

Источниками funding для платформы могут быть:

- Владельцы платформы и инвесторы, через прямые займы
- Внешние lenders: компании, фонды, частные лица
- В будущем - децентрализованные liquidity protocols, то есть DeFi

Каждый lender может открыть одну или несколько **credit lines** со своими индивидуальными условиями.

| Parameter | Description |
| :-- | :-- |
| Currency | USDC, USD, EUR, USDT, поддерживается мультивалютность |
| Type | Revolving или term |
| Limit | Максимальная сумма, доступная в рамках линии |
| Interest rate | Fixed или floating, например SOFR / EURIBOR \+ spread |
| Maturity | Дата истечения линии |
| Collateral | На первом этапе без обеспечения |

### Revolving line

Это основной тип линии. По мере погашения использованных сумм лимит восстанавливается и снова становится доступным. У каждого отдельного drawdown есть свой срок возврата, например 45 дней. Сама линия остается активной до даты истечения или до отдельного решения о ее закрытии.

## 3. Ограничения lenders: eligibility matrix

У разных lenders разный уровень толерантности к риску. Treasury-модуль позволяет платформе задавать, **какие средства каких lenders нельзя использовать для финансирования конкретных merchants**.

Примеры ограничений:

| Restriction | Example |
| :-- | :-- |
| Minimum merchant credit rating | Консервативный lender финансирует только merchants с рейтингом A или B |
| Instance exclusion | Lender не хочет экспозиции к конкретному рынку, например отдельной стране |
| Instance exclusivity | Lender работает только с одним конкретным партнером |
| Per-merchant limit | Не более \$5,000 из одной линии на одного merchant |
| Per-instance limit | Не более 30% линии может быть распределено на один instance |

Эти правила применяются автоматически каждый раз, когда система принимает решение о funding для batch-партии чеков.

## 4. Credit profile merchant

Каждому merchant платформа присваивает **credit profile**.

| Parameter | Description |
| :-- | :-- |
| Credit limit | Максимальный объем открытых batch-партий в любой момент |
| Current exposure | Сумма по уже отгруженным, но еще не оплаченным batch-партиям |
| Credit rating | A / B / C / D, назначается вручную |
| Settlement term | Стандартно 30 дней, параметр настраивается |
| Preferred settlement currency | Валюта, в которой merchant рассчитывается |

**Credit rating** влияет на eligibility для funding. Консервативные lenders могут отказаться финансировать merchants с рейтингом C и ниже. Сам рейтинг управляется вручную командой finance.

### Автоматическая блокировка при overdue settlement

Если merchant не закрывает settlement дольше допустимого порога, по умолчанию это 3 дня, платформа автоматически:

1. Блокирует отгрузку новых batch-партий этому merchant
2. Фиксирует сам факт блокировки и ее дату
3. Уведомляет администратора instance

Разблокировка выполняется только вручную и требует подтверждения администратора.

## 5. Aggregated settlement balance

Платформа поддерживает единый **liquidity pool**, то есть совокупность доступных средств по всем активным credit lines.

### Структура счетов

Для управления распределением ликвидности между instances платформа использует внутреннюю структуру счетов:

`Platform pool (all credit lines) → Instance account A / Instance account B / Reserve account`

CFO и COO могут **вручную ребалансировать выделенные лимиты** между instances через административный интерфейс. Это дает возможность гибко управлять ликвидностью, не меняя условия базовых credit lines.

## 6. Risk appetite и allocation strategy

Когда batch-партия чеков отгружается merchant, система автоматически выбирает, какая credit line должна ее профинансировать. Решение принимается на основе настроенной **allocation strategy**.

| Strategy | Logic | When to Use |
| :-- | :-- | :-- |
| Currency match | Использовать линию в settlement currency merchant | Чтобы убрать FX risk |
| Lowest cost | Использовать линию с минимальной процентной ставкой | Чтобы минимизировать стоимость funding |
| Maturity match | Использовать линию, maturity которой перекрывает settlement period merchant | Чтобы избежать maturity mismatch |
| Maximum availability | Использовать линию с наибольшим свободным остатком | Чтобы быстрее развернуть ликвидность |
| Balanced | Равномерно распределять использование между всеми линиями | Чтобы снизить зависимость от одного источника |

Помимо выбранной стратегии, система применяет **жесткие ограничения risk appetite**:

- Maximum share of any one merchant in the total pool, for example no more than 20%
- Maximum utilization of a single credit line, for example no more than 40%
- Maximum debt-to-equity ratio
- Minimum remaining maturity required for a line to be used

## 7. FX risk

Платформа работает сразу с несколькими валютами. Когда валюта credit line отличается от settlement currency merchant, платформа **берет на себя FX risk**.

**Политика:** FX risk учитывается явно и отражается в отчетности. Для каждого drawdown из линии в иностранной валюте курс фиксируется на дату транзакции. Во время settlement фактическая прибыль или убыток от курсовой разницы отражается в отчете carry P&L.

На первом этапе хеджирование не планируется. Рекомендуемый подход - отдавать приоритет стратегии **currency match**, чтобы минимизировать открытую валютную экспозицию.

## 8. Экономика treasury, carry P&L

Платформа зарабатывает на **спреде** между merchant income и стоимостью funding.

| Item | Description |
| :-- | :-- |
| **Income** | Merchant fees, то есть issuance, redemption и exchange |
| **Expense** | Проценты по credit lines |
| **FX differences** | Прибыль или убыток из-за currency mismatch |
| **Net carry** | Доход минус расходы |

**Ключевые метрики:**

| Metric | Meaning |
| :-- | :-- |
| Cost of funds | Annualized interest rate across the credit line portfolio |
| Fee yield | Percentage return generated from merchant transaction volume |
| Net spread | Difference between fee yield and cost of funds |
| Average settlement term | Average number of days from shipment to settlement |
| Overdue settlement ratio | Percentage of total volume that is overdue |
| Pool utilization | Percentage of total available limit currently used |

Если процентная ставка по credit lines выше, чем fee income, платформа фактически субсидирует операции за счет собственных средств. На фазе роста это может быть приемлемо, если ситуация явно отслеживается и контролируется.

## 9. Управление рисками

### Liquidity risk, maturity mismatch

Ситуация: credit line истекает раньше, чем merchant завершает settlement.

Контроль: система находит такие "problem drawdowns" и показывает их сумму в dashboard. Если mismatch существует, CFO получает уведомление.

### Merchant credit risk

Ситуация: merchant не платит.

Контроль: автоматическая блокировка новых batch-партий при overdue settlement, ручное понижение credit rating, управление со стороны COO.

### Concentration risk

Ситуация: слишком большая часть liquidity pool сконцентрирована на одном merchant или на одной линии.

Контроль: concentration limits, заданные в настройках risk appetite.

### FX risk

Ситуация: курс меняется между моментом drawdown и settlement.

Контроль: явный учет, отражение в carry P&L и приоритет стратегии currency match.

## 10. Операционные контроли

### Принцип four-eyes

Инициатор финансовой операции и ее утверждающий должны **всегда быть разными людьми**. Система не должна позволять одному сотруднику в одиночку пройти весь цикл операции.

| Operation | Initiated By | Approved By |
| :-- | :-- | :-- |
| Manual drawdown from a credit line | Finance | Another Finance team member or Administrator |
| Large drawdown (above threshold) | Finance / Administrator | Owner only |
| Closing a credit line | Finance / Administrator | Owner |
| Changing risk appetite | Finance / Administrator | Owner |
| Rebalancing internal accounts | Finance | Administrator / Owner |

### Velocity limits

Лимиты на объем drawdowns из одной линии в день служат защитой от ошибок и злоупотреблений. Эти лимиты настраиваются отдельно для каждой линии.

### Уведомления

Система автоматически уведомляет finance и operations-команды о следующих событиях:

| Event | Recipient |
| :-- | :-- |
| Credit line expires in N days | CFO, Finance |
| Line utilization exceeds 80% | CFO, Finance |
| Line expires with outstanding debt | CFO (urgent) |
| Automatic drawdown executed | Finance (summary or immediate) |
| Large drawdown | CFO, Finance |
| Merchant frozen due to overdue settlement | Instance Administrator |

## 11. Audit и compliance

Все операции записываются в неизменяемый audit log, включая:

- who performed the action and when
- before / after values
- IP address and confirmation of additional authentication

Финансовые записи, такие как drawdowns, начисление процентов и allocations, **нельзя изменить или удалить** после создания. Их можно только перевести в финальный статус, например `repaid` или `defaulted`.

## 13. Open Questions for Approval

**13.1 Initial lenders**\
Who will be the platform’s first lenders? What terms are expected: currency, rate, limit, maturity?

**13.2 Merchant credit limits**\
What should the standard limit be for a new merchant? Based on what criteria should it be increased? Is a multi-step approval process needed above a certain threshold?

**13.3 Default allocation strategy**\
Which strategy should be used by default? Recommendation: **currency match** to minimize FX risk.

**13.4 Large-operation threshold (four-eyes)**\
At what drawdown amount should Owner approval be required, rather than Finance approval only? The draft documentation assumes **\$10,000 USDC**, subject to approval.

**13.5 Merchant settlement currency**\
Which currencies will be accepted for merchant settlements? Who bears FX risk on conversion? Is multi-currency allocation required from day one, or are USDC-based lines sufficient initially?

**13.6 Overdue policy: automatic vs manual control**\
Automatic blocking after more than 3 days overdue is assumed. Are different thresholds needed for different merchant categories? What is the resolution process after a block is triggered?

**13.7 Cost of funding vs fee income**\
Under the current pricing model, do merchant fees cover the cost of external funding? Is financial scenario modeling required before launch?

**13.8 Collateral for lenders**\
At the initial stage, facilities are unsecured. At what portfolio size would it make sense to move to a receivables assignment structure? This could reduce the cost of funds.
