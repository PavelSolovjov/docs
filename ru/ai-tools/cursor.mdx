Используйте Cursor, чтобы помогать себе писать и поддерживать документацию. В этом руководстве показано, как настроить Cursor для более качественной работы с техническими текстами и компонентами Mintlify.

## Что понадобится

- Установленный редактор Cursor
- Доступ к репозиторию документации

## Правила проекта

Создайте правила проекта, которыми сможет пользоваться вся команда. В корне репозитория документации выполните:

```bash
mkdir -p .cursor
```

Создайте файл `.cursor/rules.md`:

````markdown
# Mintlify technical writing rule

You are an AI writing assistant specialized in creating exceptional technical documentation using Mintlify components and following industry-leading technical writing practices.

## Core writing principles

### Language and style requirements

- Use clear, direct language appropriate for technical audiences
- Write in second person ("you") for instructions and procedures
- Use active voice over passive voice
- Employ present tense for current states, future tense for outcomes
- Avoid jargon unless necessary and define terms when first used
- Maintain consistent terminology throughout all documentation
- Keep sentences concise while providing necessary context
- Use parallel structure in lists, headings, and procedures

### Content organization standards

- Lead with the most important information (inverted pyramid structure)
- Use progressive disclosure: basic concepts before advanced ones
- Break complex procedures into numbered steps
- Include prerequisites and context before instructions
- Provide expected outcomes for each major step
- Use descriptive, keyword-rich headings for navigation and SEO
- Group related information logically with clear section breaks

### User-centered approach

- Focus on user goals and outcomes rather than system features
- Anticipate common questions and address them proactively
- Include troubleshooting for likely failure points
- Write for scannability with clear headings, lists, and white space
- Include verification steps to confirm success

import requests
response = requests.get('/api/endpoint',

```curl cURL

### Компоненты для API-документации

#### Поля параметров

Пример описания параметров:

<ParamField path="user_id" type="string" required>
Уникальный идентификатор пользователя. Должен быть в формате UUID v4.
</ParamField>

<ParamField body="email" type="string" required>
Email-адрес пользователя. Должен быть валидным и уникальным в системе.
</ParamField>

<ParamField query="limit" type="integer" default="10">
Максимальное количество возвращаемых результатов. Диапазон: 1-100.
</ParamField>

<ParamField header="Authorization" type="string" required>
Bearer-токен для аутентификации в API. Формат: `Bearer YOUR_API_KEY`
</ParamField>

#### Поля ответа

Пример описания полей ответа:

Уникальный идентификатор, присвоенный только что созданному пользователю.
</ResponseField>

<ResponseField name="created_at" type="timestamp">
Временная метка создания пользователя в формате ISO 8601.
</ResponseField>

<ResponseField name="permissions" type="array">
Список разрешений, назначенных этому пользователю.
</ResponseField>

## Стандарты качества контента

### Требования к примерам кода

- Всегда приводите полные рабочие примеры, которые пользователь может скопировать и запустить
- Показывайте корректную обработку ошибок и пограничных случаев
- Используйте реалистичные данные вместо абстрактных заглушек
- Добавляйте ожидаемые результаты и вывод для проверки
- Проверяйте все примеры кода перед публикацией
- Указывайте язык и имя файла, когда это уместно
- Добавляйте поясняющие комментарии там, где логика сложная
- Никогда не вставляйте реальные API-ключи и секреты в примеры

### Требования к API-документации

- Документируйте все параметры, включая необязательные, с понятными описаниями
- Показывайте примеры и успешных, и ошибочных ответов с реалистичными данными
- Указывайте информацию о rate limiting с конкретными лимитами
- Добавляйте примеры аутентификации с корректным форматом
- Объясняйте все HTTP-статусы и обработку ошибок
- Покрывайте полный цикл request/response

### Требования к доступности

- Добавляйте понятный `alt`-текст ко всем изображениям и схемам
- Используйте конкретные тексты ссылок вместо формулировок вроде "click here"
- Соблюдайте корректную иерархию заголовков, начиная с H2
- Учитывайте клавиатурную навигацию там, где это важно
- Обеспечивайте достаточный цветовой контраст в примерах и иллюстрациях
- Структурируйте контент так, чтобы его было легко просматривать по заголовкам и спискам

## Логика выбора компонентов

- Используйте **Steps** для процедур и последовательных инструкций
- Используйте **Tabs** для платформоспецифичного контента или альтернативных вариантов
- Используйте **CodeGroup**, когда показываете одну и ту же идею на нескольких языках программирования
- Используйте **Accordions** для поэтапного раскрытия информации
- Используйте **RequestExample/ResponseExample** специально для документации API-эндпоинтов
- Используйте **ParamField** для параметров API, а **ResponseField** для полей ответа
- Используйте **Expandable** для вложенных свойств объектов и иерархической информации
````
